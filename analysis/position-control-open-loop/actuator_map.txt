29 of 38 actuators map ctrl = -1..+1 onto exactly that joint's own range.
The other 9 (cervical_extend, cervical_bend, cervical_twist, caudal_extend, caudal_bend, ankle_L, toe_L, ankle_R, toe_R) still map ctrl affinely onto
an angle, just not onto the full range: max |scale - half_range| = 0.524 rad.

kv (velocity feedback) = [-0.0] -- position feedback only; damping comes from the joints.
kp values used: [0.05, 0.1, 0.3, 0.4, 0.5, 0.6, 20.0]. The 6 spine/neck joints get kp = 20;
every limb joint gets kp <= 0.6, i.e. a soft spring rather than a stiff servo.

torque_actuators=True: force = gain * ctrl, no state feedback
(add_rodent sets gainprm0 = forcerange max and biastype = NONE)
  bias terms after conversion: [-0.0]  (0 = biastype NONE, so no qpos/qvel term)

Force authority is NOT matched between the modes. The XML's forcerange -- which is what
the torque conversion turns into the gain -- was not chosen to match kp * range, so each
joint's peak commandable torque changes when the mode changes:

ratio (torque gain) / (kp * range): min 0.18, median 0.41, max 7.16.
Position control is the *stiffer* mode at large error on most joints (median ratio < 1),
but its torque is proportional to the tracking error, so it commands little near the target,
while torque mode can command its full gain in any state. The two are therefore not a clean
feedback-loop-only contrast, and report.md carries this as a caveat.

Consequence for this analysis: under position control the action is a target joint
configuration in normalised joint coordinates, and task_obs carries the reference joint
angles (absolute, under body_target_frame=reference_root). The map from that part of the
input to a good action is static and needs no feedback. Under torque control no such map
exists: the torque that realises a target pose depends on the current state.
